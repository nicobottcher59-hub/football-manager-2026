# Phase 5.0 - Spatial Core

## Goal

Phase 5.0 creates the spatial and temporal foundation of the Match Engine.

It does **not** choose passes, simulate pressing, create shots or decide results yet.
Its purpose is to establish the mutable in-match world that later Phase 5 systems
will consume.

The simulation now has:

- a real 2D pitch measured in metres;
- 22 active player agents;
- a ball state;
- home/away orientation;
- mutable X/Y locations;
- velocity and facing direction;
- a fixed match timestep;
- deterministic match randomness;
- initial possession/kickoff state;
- fixed-step state advancement.

---

## Spatial coordinate system

The engine uses the stadium dimensions frozen into the `MatchSnapshot`.

A standard test pitch is:

```text
105 m x 68 m
```

Global coordinates use:

```text
x = 0                        x = pitch length
HOME goal  -----------------  AWAY goal

HOME attacks toward +x.
AWAY attacks toward -x.
```

Away-team positions are generated by rotating the home-perspective shape 180
degrees. This keeps left/right roles correct relative to each team's attacking
direction.

Phase 5.0 uses coarse position anchors. Tactical shape calculation replaces these
anchors in Phase 5.1.

---

## Player agents

Every starting player becomes a mutable `PlayerAgentState`.

It contains:

- stable simulation agent ID;
- home/away side;
- immutable `PlayerMatchSnapshot` reference;
- formation slot;
- assigned position;
- current X/Y location;
- velocity;
- facing direction;
- basic ball-possession flag.

Agent IDs are side-scoped:

```text
home:player-123
away:player-123
```

This prevents simulation-state collisions even if test/demo data accidentally
reuses the same player ID for both teams.

The persistent `Player` object is never mutated by this state.

---

## Ball state

`BallState` currently stores:

- X/Y location;
- velocity;
- height;
- optional current owner;
- optional last touch.

At initialization the ball is placed at the centre spot.

Ball physics, passing trajectories, rebounds and possession transfers belong to
later sub-phases.

---

## Match clock and timestep

The simulation timestep is fixed at:

```text
0.25 seconds
```

The clock stores an integer tick count and derives elapsed seconds from it.
This prevents accumulated timing drift and establishes an important contract:

> playback speed does not change simulation precision.

The engine exposes `advance_ticks()` but always executes each underlying fixed
step.

Conceptually:

```text
x1      -> consume one group of normal fixed ticks
x2      -> consume the same ticks faster
x4      -> consume the same ticks faster again
instant -> consume all required fixed ticks without visual waiting
```

Historical decision (superseded): there is no alternate simplified match algorithm for instant results.
The actual playback/UI layer is implemented later.

---

## Deterministic randomness

Each `SpatialMatchEngine` owns a `MatchRandom` initialized from
`MatchSnapshot.seed`.

The contract remains:

```text
same MatchSnapshot
+ same seed
+ same engine version
= reproducible simulation
```

Phase 5.0 already uses the seeded source to choose the deterministic kickoff side.
Future decisions, action resolution and controlled randomness must use this same
match-owned random source rather than global randomness.

---

## Initial match state

`create_initial_match_state()` converts the immutable `MatchSnapshot` into the
mutable state used during a match.

It creates:

- pitch dimensions;
- eleven home agents;
- eleven away agents;
- initial formation locations;
- the ball at the centre;
- deterministic kickoff side;
- initial possession metadata;
- a zeroed fixed-step clock.

Bench players remain inside the `MatchSnapshot` but are not active spatial agents
until future substitution logic requires them.

---

## Fixed-step movement integration

Phase 5.0 includes intentionally simple kinematic integration:

```text
new position = current position + velocity * timestep
```

Player and ball locations are clamped to pitch bounds.

When a moving player has non-zero velocity, facing is updated from the movement
direction.

This is only the spatial foundation. Phase 5.1 will calculate tactical target
positions and movement toward those targets.

---

## Playback separation

`SpatialMatchEngine` contains no x1/x2/x4 visual-speed setting.

This is deliberate.

Playback belongs outside the football simulation. A future viewer can request
one, two or four groups of ticks per real-time interval while the engine always
uses the same fixed 0.25-second simulation steps.

Tests already verify that four one-tick advances and one four-tick advance reach
the same simulation state.

---

## Tests

Phase 5.0 validates:

- vector mathematics;
- fixed timestep clock;
- pitch centre, bounds and mirroring;
- exactly 22 active player agents;
- 11 agents per side;
- ball/player coordinates remain inside the pitch;
- stadium pitch dimensions are consumed by the simulation;
- formation slot/player identity survives initialization;
- away shape mirrors home shape correctly;
- same snapshot + same seed produces the same initial state;
- kickoff side is deterministic;
- side-scoped agent IDs avoid collisions;
- fixed-step player movement;
- fixed-step ball movement;
- playback chunking does not alter the simulation path;
- invalid negative tick advancement is rejected.

Expected project result after Phase 5.0:

```text
78 passed
```

## Not implemented yet

Phase 5.0 deliberately does not implement:

- tactical movement;
- pressing;
- perception;
- decision making;
- passes;
- first touch;
- interceptions;
- dribbling;
- shooting;
- xG;
- goals;
- fouls;
- cards;
- fatigue accumulation;
- complete 90-minute match flow;
- 2D frontend rendering;
- commentary playback.

These are built incrementally on top of this core.
