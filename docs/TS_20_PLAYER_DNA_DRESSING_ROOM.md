# TS-20 - Player DNA & Dressing Room

## Scope and product contract

This release extends the managed club of an existing TS-19 career. The user
focuses on football while squad dynamics evolve automatically. The new portable
page is observational. It does not create tasks, blocking dialogs, meetings,
ultimatums, manual friendship assignments or a captain appointment system.
Tactics, Lineup, the transfer-market transaction model, youth attributes,
training/aging and medical simulation are not redesigned here.

## Runtime wiring

`DevelopmentSession` owns one `DressingRoomState` for the managed club.
Calendar progression calls `update_dressing_room()`, which advances fixed daily
steps. Batch advancement and daily advancement produce identical social state
for identical events. Weekly reviews update the influence hierarchy. The
application lock serializes HTTP access. Reading `GET /api/dressing-room`,
selecting a player, changing formation and editing the lineup do not mutate it.

Committed managed matches call `record_session_match` inside the existing
transaction. The adapter passes actual minutes, pre-match availability and
actual role-segment overlap. A substitute who never shares the pitch with a
starter receives no invented shared minutes. Missing legacy segment data does
not get approximated by the minimum of total player minutes. Repeated fixture
IDs cannot apply a second reaction. A failed match transaction restores both
player states and the room. Normal post-match base morale remains unchanged.

The real competition season transition retains people and relationships. A
results-only legacy world rewind cannot keep relationships from its future;
that distinct load path rebases neutral social history at the restored date.
Full manager-career loading restores the exact serialized history instead.

## Private personality

`Personality` is a validated, immutable value object on Player. Numeric fields
are professionalism, ambition, loyalty, pressure resistance, injury
susceptibility and leadership (1-100). Absent old values are generated by a
stable hash of player ID, not global randomness, load order, age, nationality or
match RNG. Existing characters do not reroll on save/load. These synthetic
profiles are game data, not assertions about real people.

Consumers in this release:

| Field | Consumer |
|---|---|
| Professionalism | Integration speed and eligibility for natural support |
| Ambition | Size of a small response to sustained eligible non-participation |
| Loyalty | Recovery from an influential close teammate's departure |
| Pressure resistance | A small, decaying post-defeat morale response |
| Leadership | One input to influence and automatic support eligibility |
| Injury susceptibility | Persisted only; dormant until a medical simulation exists |

Private values never enter the new public read model. After sufficient time,
qualitative observations can explain a player without revealing the numbers.
No new ability, aging, injury or training-growth consumer is claimed here.

## Evolving pyramid and network

Four tiers: team leaders, influential players, established group, developing
influence. Developing influence is not synonymous with being young. A new
veteran must earn standing; a high-influence player need not be the best player.

The initial standing uses existing teamwork, composure, private leadership and
neutral integration. It does not fabricate historical shared minutes. New
arrivals start below established players. Integration rises daily. Each weekly
review weighs current integration, peer rapport, actual participation and
observed tenure around a stable baseline. Weekly influence movement is bounded
to 1.5 points and tier changes have threshold hysteresis and a 14-day minimum
interval. A neutral first week does not demote players simply because a
different averaging formula is used for review.

Pair rapport changes slowly with compatibility, teamwork and true shared
minutes. Sustained differing participation can create modest friction; there
are no nationality-based cliques or random dramatic conflicts. Public groups
are observed connected components of strong ties, not manually assigned factions.
The network displays a selected player's closest connections to stay readable.

Support is automatic: integrated, influential, sufficiently professional
players aged at least 24 can assist young or recently arrived teammates. Each
supports at most three. This affects integration only, not ability growth.

## Conservative impact: one social channel

`PlayerState.morale` remains the ordinary football morale. A separate
`dressing_room_morale` context is **replaced**, never repeatedly added into base
morale. `effective_morale = clamp(base_morale + social_context, 0, 100)`.
The total social context is hard-clamped to **-2..+2 morale points**; this is
not an OVR/ACT adjustment of that size. Existing rating formulas and weights
are unchanged. They consume effective morale instead of base morale.
The snapshot freezes effective morale once. Reassignment during substitutions
must not apply the social context again.

Integration, recent sustained non-participation, atmosphere, close influential
departures and post-result response are components of the *same* capped context.
There are no additional independent social chemistry, confidence, condition or
base-attribute penalties. Context decays or improves as circumstances change;
there are no mandatory conversations to recover it.

Participation concern requires 28 observed days and four recent eligible
matches, with at least three below 15 minutes and a combined share below 20%.
Unavailable players are not treated as voluntary omissions. Trying a lineup,
rotating for one game or briefly benching a player does not trigger concern.

Only an influential player with observed tenure and an established tie can
cause modest departure disruption, and only for those close teammates. It is
bounded and recoverable; serial exits do not stack an unbounded penalty.
A real `Squad.remove` clears the departing player's old club morale context.
Transfer-list/loan-list flags are NOT actual squad transfers. Future completed
transfer services must advance to the event date, update membership and invoke
roster reconciliation. TS-20 does not pretend those transfers are implemented.

## Persistence and resource bounds

Manager state and safe object-graph format advance to version 4. Versions
1/2/3 load via explicit per-class migrations; missing personality and social
state are neutral/deterministic defaults, not guessed history. A v4 payload
missing mandatory state is rejected. The allowlisted codec registers the new
value objects and validates clocks, IDs, references, finite values and bounds.
Full graph references preserve player identity and the existing TS-19 library.

Downgrade requires the pre-update save backup. Do not load v4 saves with TS-19.
The room follows the existing career-save lifecycle; there is no new autosave.

Memory per club is O(players^2) for its current pair links; retained histories
are capped at 12 appearances per player, 40 events and 256 processed fixture
IDs. The 15-year stress validates this bounded social state, not 15 years of
new players, aging or a complete transfer economy.

## Frontend and validation limits

Only the portable frontend receives the new page, inserted after Tactics.
Existing editor assets are untouched. Components use vanilla JS/CSS, scoped
styles, safe text escaping and keyboard-accessible selection. The page refreshes
with normal career progression, match completion and explicit refresh; fetch
failure clears stale data and offers retry. No build or Node runtime is added.

Real Chromium renders actual assets and interacts with the screen. This
validation host blocks loopback browser navigation: the optional harness then
loads the same files into about:blank and bridges fetch to actual locked Python
read models, reporting that transport. Real HTTP contracts are independently
checked against the running Python HTTP server by pytest. This split is not a
claim that a native-Windows end-to-end browser test was executed.

See `TS_20_TEST_REPORT.md` and `reports/ts20/` for executed evidence.
